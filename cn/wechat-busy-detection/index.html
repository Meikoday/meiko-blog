微信是怎么判断「对方正在通话中」的

发表于2026-10-31|更新于2026-10-31|移动安全
|总字数:2k|阅读时长:6分钟|浏览量:

前几天想解决一件小事：不想被微信电话打扰，但又不想点「拒接」——拒接之后对方看到的是「已拒绝」，
太生硬；我想要的是「忙线」，让对方以为我正占着线在打电话。

顺着这个需求逆向了一晚上，发现微信判断「本机是否在通话中」的方式，比想象中简单，也比想象中有趣。
中间还因为两个自己挖的坑，把微信搞崩过两次。

测试环境：Android 17 / 澎湃 OS 4.0，root + LSPosed，微信 8.0.76（versionCode 3140）。
本文只讨论本机客户端行为，不含任何微信代码，也不分发修改过的安装包。

先说结论

  1. 微信判断「本机在不在通话」，不查自己的状态机，而是问系统：
    AudioManager.getMode() == 2（MODE_IN_CALL）。没有电话状态权限、或 targetSdk ≤ 30 时，
    退化成 TelephonyManager.getCallState() 等于 2（OFFHOOK）或 1（RINGING）。
  2. 「忙线」和「拒接」是两条不同的信令：忙线走 /voipack 且状态 3，拒接走 /voipanswer 且 answer=2。
  3. 8.0.76 的实际来电链路跑在 native / 独立服务里，Java 层挂不到；但只要接管它对框架接口的询问，
    它自己就会走进忙线分支。

两个细节很关键：

  • 它只认 2。MODE_IN_COMMUNICATION（3）不算数。而第三方 App 最多只能把音频模式设成 3，
    所以「写个 App 伪装通话中」这条路，在不 root 的前提下根本走不通。
  • MODE_IN_CALL 只有电话应用/系统能设，TelephonyManager 的通话状态也只有电话栈能改——
    系统状态不是普通应用能伪造的。想伪造，必须拿到 root 级别的注入能力。

原来来电界面根本不是 Activity，而是一条带「接听/拒绝」按钮的通知横幅，发通知的是 voip 的前台服务。
响铃、拒绝这些动作跑在 native / 服务层，Java 侧没有可下手的判断点。

这也顺便解释了两个我一直觉得奇怪的现象：为什么 Activity.onCreate 里从来没见过来电界面，
为什么音频模式从头到尾都是 0——因为整个通话控制压根不在我们以为的那一层。

换个方向：不去找入口，接管「被问」

既然业务逻辑在 native 里，那就别再追它了。它总要通过 Java 框架知道自己「在通话中」——
与其干预它怎么处理来电，不如直接接管它对环境的查询。

结果是决定性的：朋友再打进来，他手机上直接显示 「忙线未接听」，本机安静，不响铃不弹横幅。

而模块的计数器显示了一个有意思的事实：AudioManager.getMode 和 TelephonyManager.getCallState
被询问了多次，而微信自己的 PhoneStatusWatcher 命中 0 次。

也就是说，微信压根不经过自己的工具类，native 层直接问框架。
前面费劲找到的那个 l5.kj()，在这个版本里只是一段没人调用的遗留代码——
如果我一直盯着「微信自己的工具类」，可能到现在还在改那个永远不执行的判断。

这一夜最大的收获其实不是上面那个结论，而是两次把微信搞闪退。

第一次，我把调试日志直接打在类加载器的回调里：

结果是 StackOverflowError，微信启动即崩。

第二次，学乖了一点，但还是在钩子里读了配置：

getMode() 在音频初始化时被高频调用，而读配置本身又要加载类、走 ContentProvider，
于是再次递归，微信又崩了一次。

正确的写法只有一句话：钩子体里只做一件事。

日志、配置、计数汇总全部交给一个后台线程，每几秒刷一次。钩子越薄，越不容易把宿主搞死。

这条路的边界

能做到：

  • 所有微信来电按「电话占线」回绝，对方看到忙线；
  • 系统电话、短信、其它 App 完全不受影响——钩子只在微信进程内生效；
  • 开关热切换，不用重启微信。

做不到：

  • 伪造一个真实的通话会话。服务端看到的仍然是「没有会话」，所以这是「让微信按占线处理」，
    而不是「让对方真的以为你在通话」。
  • 只对某一个联系人生效。判断发生在会话建立之前，那里没有联系人信息。
  • 零副作用。微信会认为自己确实在通话，期间你主动外呼可能被它自己拦下，语音消息播放也可能被暂停。

一点合规提醒

这套东西只改本机客户端行为：不伪造身份、不篡改数据包、不碰服务端。风险主要不在技术层面，而在：

  • 违反微信《软件许可及服务协议》（明确禁止外挂 / 第三方工具干扰功能）→ 封号；
  • 商业化、批量操控才会显著抬高民事乃至刑事风险。

仅记录本机客户端的行为分析与实验验证，请勿用于违反服务条款的用途。
